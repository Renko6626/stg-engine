# ECL 时间标签（`60:` / `+30:`）—— 设计（2026-07-31）

> ## ⛔ 状态：**已否决，不实施**（2026-07-31，作者裁定）
>
> **否决理由**：这个特性会**系统性地让 ECL 变复杂**——它引入静态时长分析、一个新的语言构造
> （`timer_reset()`）、一类新的编译错误（"时钟未知"）和 `Builtin` 表上的必填帧耗字段，
> 而作者的日常写法用 `wait` 就够。收益与这套机构不成比例。

> 真实损失只有两条，且都是舒适度而非能力：① 读时要心算累加才知道某波在第几帧；
> ② 循环体的周期长度不显式存在于源码里。

> 不要 `FrameCost` 字段。它恰好盖住真实用例（弹幕 pattern 的循环体本身就是直线的），

## 1. 问题

写弹幕最频繁的动作是"在第 N 帧插一波"。我们只有显式 `wait(delta)`，所以**中间插一条就要重算
后面所有的 wait**。ZUN 的 ECL 每条指令自带 `time` 字段、sub 有自己的时钟，脚本读起来是一份
乐谱；我们读起来是一串手算的差值。

`docs/ecl-lang.md` 的「已知限制」自己把它列为 v1 缺口（"时间标签 `+N:` 未进 v1（显式 `wait`）"）。

现状写法与目标写法：

```ecl
// 现状：插一条 75 帧的波 → 后面每个 wait 都要重算
wait(60); batch(...);
wait(30); batch(...);     // 想在 75 插一条?  这里得改成 wait(15) + wait(15)
wait(60); batch(...);

// 目标
 60: batch(...);
 90: batch(...);
150: batch(...);          // 插 75: 时,这三行一个字都不用动
```

## 2. ZUN 的做法与我们的取舍

ZUN：每条指令的二进制头带 `time` 字段，sub 有运行期时钟；`513 timerReset` 把时钟归零
（循环里用时间标签必须手动调它，因为时钟是任务级单调的）。

**我们取纯编译器糖**（人类裁定 D-1）：编译期虚拟时钟，`60: stmt` 降低成 `wait(60 - 当前时钟)`。
理由是代价与风险的比值——不动 VM、不动 op 表、不碰 `ENGINE_VER`、World 不加字段、快照不变、
确定性零风险，而拿到的正是上面那段痛点的全部解药。

副产品：**编译期时钟反而比 ZUN 更省事**——块进入时钟归零是编译器天然知道的事，
`loop { 0: a(); 60: b(); }` 直接就对，不需要 `timerReset` 那种手动机构。

代价见 §7（两条诚实边界）。

## 3. 决策（人类裁定，实施不得偏离）

## 4. 语义

### 4.1 三种写法

| 写法 | 含义 | 降低成 |
|---|---|---|
| `60: stmt;` | 绝对：本块第 60 帧执行 `stmt` | `wait(60 - 当前时钟)` + `stmt` |
| `+30: stmt;` | 相对：再过 30 帧 | `wait(30)` + `stmt` |
| `60:` | **裸标签**（无语句） | `wait(60 - 当前时钟)` |

`wait(0)` 不发射（差值为 0 时只留 `stmt`）——保证"标签写法与手写 `wait` 写法产出逐字节相同"
这条性质（§8）在边界上也成立。

**标签可以前缀任何语句**（`var` 声明、赋值、`if`、`spawn`、表达式语句……），不只是内建调用。

**标签只在 sub 体（含嵌套块）里合法**。`xformdef` 块内**不允许**——那里已有 `@N`（相对偏移，
语义不同，D-2 维持现状），两套时序记号混在同一个块里必然坑人。在 `xformdef` 里写 `60:` 报错，
错误信息要指向 `@N`。

**裸标签是必需的**：循环体要靠它声明一圈的总时长。

```ecl
loop {
     0: batch(...);
    60: batch(...);
   120: batch(...);
   180:                 // 一圈正好 180 帧
}
```

### 4.2 时钟怎么推进

块进入时时钟 = 0。此后**只有消耗帧的东西推进它**：

| 语句 | 对时钟的作用 |
|---|---|
| `wait(K)`，K 是编译期常量 | 时钟 += K |
| `wait(expr)`，非常量 | 时钟 → **未知** |
| `+N: stmt` | 时钟 += N（未知时保持未知） |
| 内建调用 | 按 §5 的帧耗字段 |
| 用户 sub 调用 | 按 §4.4 |
| 控制流语句 | 按 §4.3 |
| 其余语句 | 不变（我们的 VM 里执行指令不消耗帧，见 §7 第一条的论证） |

### 4.3 控制流与「零耗时豁免」（D-4）

控制流语句（`if`/`while`/`loop`/`for`）之后，外层时钟转为**未知**——分支/循环各自耗时
编译期算不出来。

**但零耗时豁免**：若该控制流语句的**所有**子块都是零耗时（递归判定：不含 `wait`、不含
帧耗未知的内建、不含帧耗未知的 sub 调用），则它不污染时钟。

这条豁免防的是一个很烦的 papercut：

```ecl
 0: fire(...);
if global(GVAR_RANK) >= 2 { set_global(20, 1); }   // 零耗时 → 不污染
60: fire(...);                                      // 仍然合法
```

不加这条，一个纯判断用的 `if` 就会让整段时间轴报废。

**时钟未知时用绝对标签 = 编译错误**，报错必须指明**从哪一条语句起未知**，并提示改用 `+N:`
或 `wait()`。相对标签 `+N:` **永远合法**（它就是 `wait` 的别名，不依赖时钟已知）。

### 4.4 用户 sub 调用（D-7）

普通 `sub` 被同步调用时也可能消耗帧——`sub helper() { wait(30); }` 就是 30 帧。这既不是
`wait` 语句也不是内建，是第三条漏网路径。**demo 里真实存在**：`godot/ecl/demo/main.ecl` 的
`main()` 里 `stage1(); boss_battle();` 两个普通 sub 调用，内部都有等待。

**判定取传递性布尔，两态**：

- **Zero** —— 该 sub 传递性地不含任何帧耗（不含 `wait`、不含帧耗非零的内建、其调用的所有
  sub 也都是 Zero）。**不污染时钟。**
- **Unknown** —— 其余一切。**污染时钟。**

不做"Const(n)"这一档（不做完整时长代数）：直线且全常量 `wait` 的 sub 在真实脚本里罕见，
而算法复杂度差一个量级。递归本就被禁（`slots` 阶段已检查并报环路径），故调用图是 DAG，
传递闭包必然终止。

### 4.5 `mark(id) { ... }`

`mark` 是语句级垫片：codegen 发一条 JMP 跳过落点，落点后跟补偿块（`codegen.rs` 的
`mark_here` + `scan_mark_compensation`）。**正常流里补偿块是被跳过的**，故它对正常流的帧耗
= 0，**不污染时钟**。

补偿块内部若含 `wait`，那只在中段启动路径上消耗帧——而编译期时钟建模的是**正常流**。
这个不对称是 `mark` 本身的既有性质（中段启动本就不重放被跳过的帧），不是时间标签引入的。
补偿块内部允许写标签，其时钟按块级规则从 0 起（那是中段启动路径的时间轴）。

### 4.6 `wait_spell()`

`wait_spell()` 是 parse 阶段的语句级糖，展开成 `while spell_timer() >= 0 { wait(1); }`
（`parse.rs`）。展开后是个含 `wait` 的 `while` → 按 §4.3 污染时钟。**结论正确，但那是碰巧**
——它之所以被兜住是因为展开成了控制流，不是因为有人设计过。§5 的守卫才是把这类情形
系统性接住的机制。

## 5. 帧耗声明：结构性守卫（D-6）

**今天我们是安全的**：`OP_WAIT` 是全 VM **唯一**的 `Exec::Yield` 来源（`crates/stg-core/src/ecl/vm.rs`
的 `OP_WAIT` 分支），且没有任何 syscall 写 `task.wait`。所以当前只有 `wait` 消耗帧。

**但这是个会到期的安全。** ZUN 那边有一整排条件阻塞指令，其中好几条是我们迟早要加的：

| ZUN ins | 语义 | 耗时性质 |
|---|---|---|
| `548 diffWait(S,S,S,S)` | 按难度从四个值里选一个等 | 编译期未知、运行期已知 |
| `519 dialogWait` | 等对话脚本结束 | 条件阻塞 |
| `520` | 等到场上没有 boss | 条件阻塞 |
| （TH8 时间轴）`ins_10` | 等到场上没有可击破的敌 | 条件阻塞 |
| （TH8 时间轴）`ins_13/14` | 跨时间轴会合（等另一条时间轴发信号） | 条件阻塞 |

`diffWait` 尤其近——难度分档是「手感梳理」列的第 3 条缺口，独立成刀时很可能就带它。

**一旦加了这类内建，编译期时钟会静默失准**，而 §4.2 的"非常量 `wait` 污染时钟"**兜不住**
（它根本不经过 `wait` 语句）。

**守卫：`Builtin` 结构体加一个必填的帧耗字段。**

```rust
/// 该内建在运行期消耗多少帧——时间标签的编译期时钟据此推进（时间标签刀 2026-07-31）。
/// **必填**：`BUILTINS` 是穷举表，加字段等于逼所有现存与将来的内建表态，漏一个编译不过。
pub enum FrameCost {
    /// 不消耗帧。当前全部 39 个内建都是这一档（`OP_WAIT` 是 VM 唯一的 yield 来源）。
    Zero,
    /// 消耗编译期已知的固定帧数。当前无人使用，为对称保留。
    Const(u32),
    /// 消耗编译期未知的帧数（条件阻塞 / 难度相关）。**时钟据此转为未知。**
    Unknown,
}
```

这把"将来加阻塞内建时记得处理时钟"从一条**要记住的规矩**变成了**不表态就编不过**——与本仓
既有的 exhaustive `Init`、`BUILTINS` 两处穷举名单断言是同一个套路。

将来真加了 `diff_wait`，它自然把时钟污染掉：其后的绝对标签报错、`+N:` 照常工作。
**优雅降级，不是静默错误。**

## 6. `wait` 的 u16 截断陷阱（D-8）

`OP_WAIT` 的实现是 `task.wait = frames as u16` —— **i32 截断成 u16**，且有测试钉死这个语义
（`wait(65536)` → **0**、`wait(-1)` → 65535）。

所以 `70000: fire()` 会降低成 `wait(70000)`、运行期截断成 4464，**静默错到离谱**。

编译期知道这个差值，所以这是编译器唯一能挡的地方：**降低后的等待值 > 65535 → 编译错误**，
报错要给出实际差值。65535 帧 ≈ 18 分钟，正常内容压不到；这是纯防呆。

## 7. 两条诚实边界

**① 预算耗尽会让编译期时钟与真实帧数分家。**
`run_tasks` 里 `wait > 0` 的任务**总会**递减（这个检查排在预算检查**之前**），所以纯等待中的
任务不受影响。但**正在执行指令**的任务撞上全局预算耗尽（`GLOBAL_BUDGET = 65536` op）会本帧
不跑、次帧重来（静默，不 Fault——"这一帧没轮到它，不是它的错"）。此时实际帧数比标签多，
且纯糖方案**不会追回**；ZUN 的运行期时钟会自动追平。

正常负载压不到，但它是纯糖方案的固有代价，**必须写进手册**。

**② 时钟只算 `wait`，不算指令执行本身。** 我们的 VM 里执行一条指令不消耗帧（只有 `OP_WAIT`
让出），所以"时钟 = 各段 `wait` 之和"是精确的——这条性质是 ① 之外的全部前提。

## 8. 实现位置与测试

### 8.1 位置：parse 之后的独立 desugar pass

当前管线（`crates/stg-ecl-compiler/src/lang/mod.rs`）：
`parse` → `entryck::check` → `typeck::check` → `slots::allocate` → `codegen::generate`。

**时间标签的降低放在 `parse` 之后、`entryck` 之前**，作为一个独立 pass 重写**未定型 AST**。

这样能让"纯语法糖"这个说法**结构上成立而不只是口号**：desugar 之后的 AST 里**不存在**
时间标签这个概念，`entryck`/`typeck`/`slots`/`codegen` 四个阶段零改动，它们根本不知道这个
特性存在。

该 pass 需要 `BUILTINS` 表（读帧耗字段）与调用图（§4.4 的传递性判定），两者都不需要类型信息。

**词法无歧义**：现有语言里语句不可能以整数字面量开头（表达式语句必须消费值，裸 `60;` 本就
非法），也没有一元 `+`（只有一元负号）。故 `60:` 与 `+30:` 两个记号不与任何既有语法冲突，
不需要新关键字。

倒退标签（D-5）、时钟未知（§4.3）、截断（D-8）三类错误在这个 pass 里报，带行列。

### 8.2 测试

**判别腿只有一条真正要紧的：**

```ecl
 60: a();
 90: b();
```

必须降低成 `wait(60) … wait(30)`，**不是** `wait(60) … wait(90)`。天真实现会把绝对值直接
当 wait 参数发出去，而这个错误在"只有一条标签"的测试里**看不出来**——第一条恰好是对的。
这条测试是整个特性的守门人。

**最强的一条**：同一段逻辑，标签写法与手写 `wait` 写法编译出的 `EclImage` **逐字节相同**。
这是"纯糖"的最硬陈述——不相等就说明降低不干净。

其余各钉一条：

| 测试 | 守什么 |
|---|---|
| `loop { 0: a(); 60: b(); }` 第二圈从 0 起 | 块级归零（D-3） |
| `if` 无 `wait` → 其后绝对标签仍合法 | 零耗时豁免（D-4） |
| `if c { wait(5); }` → 其后绝对标签报错 | 豁免的**负向腿**（防豁免过宽，把有耗时的也放过） |
| `60: a(); 30: b();` 报错 | 倒退（D-5） |
| 时钟未知后 `+N:` 仍合法 | 相对标签不依赖时钟 |
| 裸标签 `180:` 单独成句 | §4.1 |
| 调 Zero sub 不污染 / 调 Unknown sub 污染 | §4.4 两态各一腿 |
| 差值 65536 报错、65535 通过 | 截断闸的**阈值下沿**（D-8；只测 65536 会让 `>=` 与 `>` 写反也绿） |
| 把某内建的帧耗改成 `Unknown` → 其后绝对标签报错 | §5 守卫真的接线了（**变异式**：否则字段可能只是摆设） |
| `xformdef` 里写 `60:` 报错且指向 `@N` | §4.1 的块类型限制 |
| `mark` 语句其后绝对标签仍合法 | §4.5（正常流零耗时） |

### 8.3 破坏面

- **金向量逐字节不变**——纯编译器改动，现有脚本一个标签都没用。**两个方向都要验**
  （"该同的同"）。
- **不碰** `ENGINE_VER` / VM / op 表 / World / 快照 / 存档格式。
- 文档：`docs/ecl-lang.md` 的「语句」节加语法、「已知限制」里那条"时间标签 `+N:` 未进 v1"
  删除、§7 两条边界写进坑清单。
- `editors/vscode/stg-ecl/syntaxes/ecl.tmLanguage.json` 是**手写**的，加一条时间标签的高亮
  规则（不加的话 `60:` 会被高亮成普通整数）。

## 9. 明确不做

- 运行期时钟 / `WAIT_UNTIL` op / `timer_reset()`（D-1）。
- 分支等长时保住时钟、`for i in 0..a..b` 常量次数时算总时长（完整时长代数）——YAGNI，
  等真被咬到再说。
- 用户 sub 的 `Const(n)` 帧耗档（D-7）。
- ZUN 的"时刻已过就立刻执行"（D-5 取报错）。
- 改 `xformdef` 的 `@N`（D-2）。
- 迁移 demo / 金向量脚本到新写法（D-9）。

## 10. 与另两条手感缺口的关系

「ECL 手感梳理」列了四条硬缺陷，本刀只做第一条。另两条**各自独立成刀**，与本刀无共享机制、
无顺序依赖：

- **shooter 机制**（预存 fire 参数集，参照 ZUN `et*` 族 41 条）——引擎侧新状态，要进
  World/校验和/快照预算/`ENGINE_VER`。收益最大、代价也最大。
- **难度分档**（参照 ZUN `rankI3/F3`、`diffI/F`、`diffWait` 与每条指令的 `rank_mask`）——
  其中 `diffWait` 会是本仓**第一个** `FrameCost::Unknown` 的内建，届时 §5 的守卫首次通电。

第四条（敌人运动动词只有 `move_to` 一个）与第五组（数学面暴露 / `nearest_enemy` 死代码 /
一处陈旧文档）另行安排。

## 11. 本文中独立成立的查证（不随否决作废）

本特性被否决，但下面三项是对**现有代码**的查证，与时间标签无关，独立成立：

**① `wait` 的 u16 截断是当前的活陷阱，且手册没写。**
`OP_WAIT` 的实现是 `task.wait = frames as u16`，测试钉死了 `wait(65536)` → **0**、
`wait(-1)` → 65535（`crates/stg-core/src/ecl/vm.rs` 的 `mod tests`）。
而 `docs/ecl-lang.md` 的语句节只写了 "`wait(n);`（n: int 帧）"，**全文没有一处提到截断**
（已 grep 确认）。所以今天写 `wait(70000)` 会静默变成 4464。
→ **归"小问题清洗"那一刀：手册补这条坑。**

**② `OP_WAIT` 是全 VM 唯一的 `Exec::Yield` 来源，且无任何 syscall 写 `task.wait`。**
即当前只有 `wait` 消耗帧。这条事实在别处也有用（任何涉及"脚本时序"的推理都依赖它）。

**③ ZUN 侧的条件阻塞指令清单**（见 §5 的表）：`548 diffWait` / `519 dialogWait` /
`520`（等 boss 清空）/ TH8 时间轴的 `ins_10`（等敌清空）与 `ins_13·14`（跨时间轴会合）。
→ **对"难度分档"那一刀直接有用**：`diffWait` 会是我们第一个"耗时编译期未知"的内建。
