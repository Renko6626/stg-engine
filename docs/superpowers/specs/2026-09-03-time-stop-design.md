# 自机能力刀 —— 时间停止 + bomb（设计，2026-09-03）

> 状态：**已评审拍板，待写实施计划**。本文是 brainstorming 环的产出，口径由人类逐条裁定
> （下文「人类拍板记录」逐条留痕）。实施计划另起 `docs/superpowers/plans/`。

## 1. 是什么 / 为什么

本刀做**两件自机能力**：**时间停止**与 **bomb**。合并的理由见 §8——它们共用同一套能力
触发骨架，分开做会把骨架写两遍。

时间停止有两个方向，共用同一套冻结机制：

- **玩家技能（停敌人）**：自机照常移动与开火，敌弹、敌人、背景全部冻结；**自机自己打出去的
  弹也冻在出发点**，解除瞬间一起放出去。是一个"安全窗 + 蓄力"的机制。
- **ECL 演出（停玩家）**：脚本把自机定住（不能移动、不能发新弹，已在场上的自机弹也冻住），
  敌方照常行动。是一个惩罚型演出。

bomb 是自机的另一件能力：**无敌 + 全屏消弹 + 范围伤害 + 全屏吸道具**，并且**在决死窗口内
按下可以撤销死亡**（deathbomb）。它同时销掉 `docs/follow-ups.md` E 组那条"bomb 那一刀开工前"。

### 这件事在本引擎里的真实形状

**时间停止不是一个开关，是一次世界时钟的分裂。** 引擎现在只有一根时钟 `World.frame`
（相位 10 `advance` 里 `+= 1`），所有计时器都**隐式**挂在它上面——没有任何一处显式问过
"这一帧世界该推进多少"。加时停 = 把全部时钟消费者裁成"跟世界时间走"与"跟真实帧走"两类。
那张裁定表（§6）就是本设计的正文，其余都是实现。

## 3. 冻结分区：三组

- **A｜自机的*主动行为***：移动、发弹动作、（将来）bomb 与时停本身的使用。
- **B｜自机弹的飞行**。
- **C｜世界的*演化与裁决***：敌弹 / 敌人 / 全部 ECL 任务 / xform 游标 / 作用区 / 道具 /
  背景 / **自机生死状态机计时（决死窗口、重生无敌）** / 符卡计时 / 相位 6 与 7。

于是：**玩家技能 = 冻 B+C**，**ECL 演出 = 冻 A+B**。

两条不显然但重要的归属：

- **自机弹归 B 而不是 A**：发弹动作与弹的飞行分属不同侧——这正是"自机弹冻在出发点"的由来。
  B 在两种时停里都冻，不是巧合，是"弹一旦离开枪口就不再属于自机"的自然结果。
- **自机被动状态计时归 C 而不是 A**：它不是自机的行动，是**世界对自机的裁决**。放在 A 会造出
  一个怪状态——ECL 演出定住自机、自机中弹进决死窗口，而窗口计时被冻、又不能 bomb，于是永远
  挂在决死窗里。归 C 之后两个方向都自洽。

## 4. 相位 6/7 的门禁规则（推导，非约定）

裁定 #3 不能照搬到 ECL 演出那一侧——玩家被定住却又免伤，那个演出就毫无威胁。门禁不能挂在
"是否冻结"上。真正的判据是：**伤害的来源是敌方弹幕的运动**，故

> **相位 6/7 只在 C 组在跑时进行。**

| 情形 | C | 相位 6/7 | 是否符合意图 |
|---|---|---|---|
| 玩家技能 | 冻 | 不跑 | ✔ 绝对安全窗 |
| ECL 演出 | 跑 | 跑 | ✔ 定住你，弹幕照来 |
| 两边同时开 | 冻 | 不跑 | ✔ 全场静止 |

一条规则覆盖三种组合、零例外。

**顺手堵上的一个漏洞**：符卡计时住在相位 7 `settle_spells` 尾 ⇒ 玩家技能期间符卡不倒计时，
**没法用时停白嫖 survival 卡**；ECL 演出期间符卡照计时。同一条规则，两个方向都对，不需要
为符卡另写规矩。

**两条玩法可见的导出后果**（已确认接受）：时停期间**不能吃道具**（道具在 C 组、拾取判定在
相位 6，两头都停）；时停期间**不计擦弹**。

## 5. 世界侧状态与相位门禁

### 状态：只加一个字段

```rust
/// [0] = 玩家技能剩余帧（冻 B+C），[1] = ECL 演出剩余帧（冻 A+B）
pub(crate) freeze_left: [u16; 2],
```

**掩码是推导出来的，不存**：`A 冻 ⇔ left[1] > 0`、`C 冻 ⇔ left[0] > 0`、`B 冻 ⇔ 任一 > 0`。
存掩码只会多一个与倒计时不同步的机会。**时停状态本身只占 4 字节**（本刀 `World` 的总增量还
含 §9.1 的 `PlayerState.time_stops`，两名自机各 1 字节）。它自动进校验和、随快照回滚——
**对 M3 rollback 是免费的**，不需要任何特殊处理。

### 死锁与它的解（重要）

若"玩家技能的倒计时跟 A 走、ECL 演出的倒计时跟 C 走"，则两边同时开启时：A 被演出冻住 ⇒
技能倒计时不走；C 被技能冻住 ⇒ 演出倒计时不走。**两个都永远解除不了，世界卡死。**

解：**两个倒计时都挂在真实帧上，在相位 0 `begin` 里无条件递减**，不属于任何一组。这也是
`World.frame` 必须照常推进的理由——它是唯一那根不受任何时停影响的轴，回放 / 校验和 /
联机握手都以它为准。

### 相位门禁

| 相位 | 门禁 | 说明 |
|---|---|---|
| 0 `begin` | 恒跑 | 两个倒计时在这里递减 |
| 1 `decode_input` | 恒跑 | 输入照译码进 `players[i].input`（它入校验和）；A 冻时相位 3 忽略它，不在这里拦 |
| 2 `run_tasks` | C | 全部 ECL 任务 owner 只有 ENEMY/STAGE/BULLET，**没有 PLAYER** ⇒ 冻 C 就是整条跳过，不必逐任务筛 owner |
| 2 导演槽 | 恒跑 | 宿主的槽、不是世界的一部分；宿主自己看 `WorldView` 决定动不动 |
| 3 `update_players` | A / C 各一半 | 唯一需要内部拆开的相位 |
| 4 `run_transforms` | C | |
| 5 `integrate` | B / C 各一半 | 自机弹那趟归 B，其余归 C |
| 6 `collide` · 7 `settle` | C | §4 的规则 |
| 9 `cleanup` | C | 冻 C 时没有新的越界/消弹标记产生，无需回收 |
| 10 `advance` | 恒跑 | `frame` 恒增 |

**背景停滞不是"什么都不做"就能得到的**：背景动画由 `frame − bg_phase_frame` 驱动，而
`frame` 恒增 ⇒ 只冻别的，背景照样会走。故**冻 C 时同步 `bg_phase_frame += 1`**，让
"背景经过的时间"不增长。不写这条就会出一个很难查的 bug：一切都停了，只有背景在动。

`WorldView` 加只读口 `freeze_left()`，供表现层画停时效果。

## 7. 为什么砍掉实体级冻结

路线三（每池加冻结位）唯一能做的是"只冻一部分实体"——例如"全场静止只有 boss 在动"的演出。
裁定 #2 已经否掉那种演出走引擎，理由是**它可以靠 ECL 脚本演出来**：让敌人和它们的弹"约定好
停下"。这条逃生口是现成的，`xform` 的 **51 号 `WAIT_SIGNAL`**（停驻等信号脉冲，边沿触发）
配 `set_speed(0)` 就是字面意义上的自我冻结：

```
[0] set_speed(0)        // 停住
[1] WAIT_SIGNAL ch=0    // 停驻等脉冲
[2] set_speed(2.0fx)    // 收到就继续
```

**诚实的限制**：它只对当初就写了这段 xform 的弹有效，**不能追溯冻结已经在场上的任意弹**。
接受这条限制是拍板的一部分，不是漏做。

选路线一即**放弃实体级豁免**。将来真要做"只有 boss 在动"且不接受脚本方案，那是另开一刀、
需要重新评审的事，**不是在本设计上打补丁**。

## 8. 共用骨架：自机能力

时停与 bomb 共用的**不是冻结机制**（bomb 恰恰要求相位 6/7 照跑），而是**能力触发骨架**：

> 输入沿 → 资源检查 → 门禁四条 → 扣资源 → 写一次性效果 → 固定时长状态机逐帧倒数 → 清状态

两者都是它的租户，各自额外用一套东西：时停用 `freeze_left`，bomb 用 `FieldPool` /
`attract_all_items` / `invuln`。**是否真的抽出一个共用函数，留给实施计划按代码形状定**
——过早抽象与写两遍同样是成本。本 spec 只承诺"两者的门禁与扣费顺序一致"，那是可测的性质。

**触发门禁四条（两者同构）**：动作位沿触发 + 资源 > 0 + 该能力当前未在进行 + 自机处于可用
状态。第四条是唯一不同的：时停要 `LIFE_ALIVE`，bomb 是 `LIFE_ALIVE` **或** `LIFE_DEATHWINDOW`
（后者即 deathbomb，§10.2）。

## 9. 时停的两个入口

### 9.1 自机侧（玩家技能）

**输入位**：`define_actions!` 加 `BTN_TIMESTOP = 7, Edge`（沿触发，同 `BTN_BOMB`）。
`input.rs` 已写死纪律——**位 = 0 必须等价旧行为**，故加位不是回放格式的破坏性变更（旧回放该
位恒 0）。副作用：`actions_vocab_hash` 变 ⇒ `input.rs` 那条"词表变更须有意识地更新此值"的
测试会红，**这是它设计出来就要做的事**，照更新。

**资源**：`PlayerState` 加 `time_stops: u8`；`Loadout` 加同名字段（开局装备）；新增
**`513 add_time_stops(delta)`**——号是族内顺延（510/511/512 = `add_lives`/`add_bombs`/
`add_power`），语义照抄（允许负、饱和钳）。没有这条 syscall 这个机制无法补给。

**触发**住相位 3、归 A 组。门禁四条：`BTN_TIMESTOP` 沿 + `time_stops > 0` +
`freeze_left[0] == 0` + 自机 `LIFE_ALIVE`。效果两句：`time_stops -= 1`、
`freeze_left[0] = TIMESTOP_FRAMES`。时停期间再按 = **no-op 且不扣资源**。
`TIMESTOP_FRAMES` 走 C14 ① 段注入（脚本与手册可引用，不必硬编），初值 **180**（3 秒）。

**时序语义（必须钉死）**：相位 3 写 `freeze_left[0] = N` ⇒ **当帧相位 4 起即已冻**，此后相位 0
逐帧递减，世界总共少走 **恰好 N 帧**。这与 `ENGINE_VER 11→12` 那个 `wait` 差一帧的坑是同一
类，判别式测试取 **N=1 与 N=2 两点**——只测 N=1 的话"恒冻一帧"的错实现照样绿。

### 9.2 ECL 侧（演出）

**`560 time_stop_player(frames)`**，1 参，写 `freeze_left[1]`。5xx 是局面族，55x 已被表现锚点
占用，开 56x 小组（百分区制：新号落族内、永不乱序追加）。

- 参数收窄照 **D19 判例**：`u16::try_from` 失败 ⇒ P4-b 整条 no-op + `contract_viol` +
  `BAD_ARGS`，**不钳位、不 Fault**。
- **`time_stop_player(0)` = 立即解除**——天然的取消 API，不另开 syscall。
- 重入取**覆盖**（后写为准），不取最大、不叠加：脚本是权威，覆盖可预测。
- owner 类别无限制（STAGE 任务常发）。

表层内建同名；改 `builtins.rs` 后**必须重跑 `gen-ecl-meta`** 同步 `7-reference.md` 生成段与
VS Code 元数据。

### 9.3 两边同时开

掩码取并集 ⇒ `0b111` 全场静止。两个倒计时各自在相位 0 独立递减，谁先到 0 谁先解除。
**不需要任何冲突裁定规则**——这是三位掩码白送的。

## 10. bomb

### 10.1 现状盘点：机制债几乎为零

三件效果的机制**都已经在仓里**，缺的只是调用方（逐条已核实）：

| 效果 | 现状 | 缺什么 |
|---|---|---|
| 玩家无敌 | `invuln` 字段在，**碰撞侧已消费**（`world/collide.rs` 行 1/2 跳过无敌自机），有测试 `collide_skips_invuln_player` | 只缺"谁把它设上" |
| 全屏吸道具 | **`attract_all_items(player)` 已实现**（`world.rs`，P4-b 契约 + 测试），doc 原话即"bomb / 导演 / 将来 ECL syscall 的通用入口" | 只缺调用方 |
| 范围伤害 / 消弹 | `FIELD_DAMAGE` 已在碰撞行 6/7 消费、`FIELD_CLEAR_BULLETS` 整套就位；`create_field` 是公开写 API | 只缺"铺哪些 field" |
| 符卡资格作废 | **已接线**：`spell.rs` 那句 `bomb_phase != 0 ⇒ capture_ok = 0` 一直在等一个真会设 `bomb_phase` 的人 | 什么都不缺 |
| 补给 | `ITEM_BOMB_PIECE` + `PIECES_PER_BOMB = 5` 的入账 B12 那刀已修好 | 什么都不缺，**不需要新 syscall**（与时停不同） |

真正缺的只有：`bomb_phase`/`bomb_timer` 的状态机逻辑（字段在、逻辑无）、相位 3 消费
`BTN_BOMB`（词表里 `BTN_BOMB = 5, Edge` 早就有）、资源扣减、以及 §10.3 那张描述表。

### 10.2 起爆与 deathbomb

**门禁四条**（§8 骨架）：`BTN_BOMB` 沿 + `bombs > 0` + `bomb_phase == 0` +
`life_state ∈ {LIFE_ALIVE, LIFE_DEATHWINDOW}`。最后一条就是 deathbomb——**主动 bomb 与决死
救人是同一条路径**，只是入口状态不同，不写两套逻辑。

**deathbomb 的实现成本接近零**，因为引擎结构早就保证了：进入决死窗口时（`world/settle.rs`）
**只设 `life_state` 与 `state_timer`，`lives` 一点没动**；扣命只发生在 `commit_death`，而它
只在 `state_timer` 归零时才跑。所以决死救人 = 把 `life_state` 拨回 `LIFE_ALIVE`、
`state_timer` 清零，**不需要任何退款逻辑**。M0-7 留 stub 时结构就铺好了。

**起爆当帧做六件事**，全是对既有机制的一次调用：

1. `bombs -= 1`、`bomb_phase = 1`、`bomb_timer = cfg.frames`
2. 若来自 `LIFE_DEATHWINDOW`：`life_state = LIFE_ALIVE`、`state_timer = 0`（`lives` 不动）
3. `invuln = cfg.invuln`
4. 按 `cfg.fields` 逐条 `create_field`（声明序，I4）
5. 若 `cfg.attract_items`：`attract_all_items(i)`
6. （无第七件——field 各自 `life` 倒数、相位 9 自己回收，bomb 不管它们的生死）

此后相位 3 每帧 `bomb_timer -= 1`，归零清 `bomb_phase`。

**`bomb_timer` 归 C 组**（与 `invuln`、决死窗口同属"世界对自机的裁决"）⇒ 时停期间 bomb 不
流逝、不浪费无敌帧。这不是新规矩，是 §3 分区模型自动给出的。

### 10.3 描述层：`CharacterCfg.bomb: BombCfg`（表驱动）

"哪个自机的 bomb 铺哪些 field、铺多久"是**内容数据**，不是代码。与 `ShotTypeCfg` 完全同构
（M0-17 立下的先例：角色参数进表、`&'static` 穿线不进 `World`），也不违反 P5（数据不是回调）。

```rust
pub struct BombCfg {
    pub frames: u16,          // 效果时长
    pub invuln: u16,          // 无敌帧（允许 > frames，见下）
    pub attract_items: bool,  // 起爆当帧是否全屏吸道具
    pub fields: Box<[BombField]>,   // 起爆时铺的作用区，按声明序
}

pub struct BombField {
    pub origin: BombOrigin,   // 圆心来源
    pub radius: Fx,
    pub flags: u8,            // FIELD_CLEAR_BULLETS | FIELD_DAMAGE
    pub dmg_per_frame: u16,
    pub life: u16,
}

pub enum BombOrigin { FieldCenter, PlayerAtCast }
```

`BombOrigin` 用**枚举而非 bool**，并在起爆处以**穷尽 `match`** 消费：加变体而忘了处理 ⇒
**编译不过**（D18 立下的押运手法）。将来"锁定敌人的 bomb"就是加一个变体 + 上层每帧重铺，
引擎主体不动。

**v0 内容（character 0）**：`frames = 120`、`invuln = 120`、`attract_items = true`，两条 field
——① `FieldCenter` / `FIELD_RADIUS_FULLSCREEN` / `CLEAR_BULLETS` / `life = 120`；
② `PlayerAtCast` / `radius = 120` / `DAMAGE` / `dmg_per_frame = 4` / `life = 120`
（120 帧 ≈ 480 伤害，约半管风铃卡血）。

**数字只住表、不进 C14 常量**——否则 `BOMB_FRAMES` 会同时活在常量与表里，成为第二真相源
（F9/D18 刚教训过的那一类）。时停的 `TIMESTOP_FRAMES` 仍是引擎常量，因为它不在任何表里。

**`invuln` 取等长（120）是 §2 裁定 #9「单阶段」的直读**。要提醒的是：另一种做法是让无敌比
效果长一截，解决"**炸完立刻死**"（效果一结束、弹幕已重新铺满，而无敌同时结束）。真要那条
尾巴，**就是把表里的 `invuln` 调大，不改任何结构**——`invuln` 本来就是独立字段。

**`validate()` 要加的**：`radius` 双边入 `[0, MAX_ENTITY_RADIUS]`（`create_field` 也会钳，
表校验先拦更响亮）、`flags` 只含已定义位、`frames > 0`、每条 field 的 `life > 0`。

### 10.4 持续消弹是白送的

消弹 field 的 `life = frames` 而非 1 ⇒ 它在整段 bomb 期间存在，**逐帧消掉新飞进来的弹**。
bomb 的"保护时长"因此天然成立，不需要每帧重铺、也不需要额外机制。

## 11. 测试策略

`CLAUDE.md` 写死了金向量闸门抓不到行为回归（它只做跨平台对拍、仓内无基线），所以本刀的
正确性**全靠单测**。

### 11.1 主测：用整块 World 校验和押运整张裁定表

建一个"什么都在动"的世界（弹在飞、敌在动、道具在落、作用区在倒数、ECL 任务在跑、自机在
移动），开**全场静止**（两位都开）跑一帧。此时按裁定表，**只有 `frame` 与 `freeze_left` 该
变**（输入喂空 ⇒ `players[i].input` 也不动）。做法是把这两个"恒跑"字段抹回步进前的值，再比
**整块 World 的校验和**：

```rust
let before = snapshot(&w);            // copy_into
step_full_freeze(&mut w);
w.body.frame = before.body.frame;     // 抹掉两个恒跑字段
w.body.freeze_left = before.body.freeze_left;
assert_eq!(w.checksum(), before.checksum(), "全场静止下除恒跑字段外不得有任何变化");
```

杀手级好处：**将来谁往 `World` 加新计时器而忘了裁定，这条测试自动把它照出来**——新字段由
`#[derive(Checksum)]` 自动进哈希（P6 全量校验），不需要有人记得回来补断言。

第二条腿只开玩家技能位（冻 B+C）：断言 C 组字段逐位不变、而自机坐标与自机弹数**变了**。
没有这条的话，"门禁写成恒冻一切"也能让第一条腿绿。

> **注**：`stg-world-design.md` 的 D11 承诺过一个 `checksum_report()`（debug 逐字段哈希清单），
> 本设计**不依赖它**——它至今没有实现（已核，全仓无此函数）。有它的话上面这条测试红了能
> 直接指名是哪个字段，没有它只能说"有东西变了"。是否顺手实现留给实施计划权衡，**不是本刀
> 的前置**。

### 11.2 时停的八条判别腿（每条写明判别力来源）

1. **时序**：`N=1` 与 `N=2` 两点——只测 N=1 则"恒冻一帧"的错实现照样绿。
2. **死锁**：两边同时开，两个倒计时都在减、都能解除。把任一倒计时挪到组门禁之后 ⇒ 当场死循环。
3. **符卡不白嫖**：survival 卡 + 时停 N 帧 ⇒ `frames_left` 恰好少走 N。
4. **蓄水池**：时停中按住射击 ⇒ 弹数增长而每颗坐标**逐位不变**；解除后同一批开始移动。
5. **规则不能照搬**：ECL 演出方向（冻 A+B、C 跑）自机**照样会被打死**。写成"冻结即免伤"这条
   立刻红——它守的正是 §4 那条门禁规则。
6. **背景**：冻 C 一帧后 `frame − bg_phase_frame` 不变。守 §5 那个坑。
7. **资源**：时停中再按不扣资源；`time_stops == 0` 时按无效。
8. **ECL 收窄**：`time_stop_player(65536)` ⇒ no-op + `contract_viol` +1（D19 判例）。

### 11.3 bomb 的五条判别腿

1. **决死窗口内 bomb ⇒ 复活且 `lives` 未减**。
2. **窗口外（已 `commit_death`）bomb ⇒ 救不回来，`lives` 已减**。①② **成对才有判别力**——
   只写①的话，"任何时候 bomb 都能救"的错实现照样绿。
3. **伤害圆判别式**：圈**内**敌掉血、圈**外**敌不掉血。圆心重合式的摆法测不出半径映射
   （`CLAUDE.md` 点名的 M0-7 教训）。
4. **伤害圆不跟随**：起爆后把自机挪走，圆心不动、判定不变。守裁定 #10 的后半句。
5. **持续消弹**：起爆后第 60 帧新发射的弹**也被消掉**。写成 `life = 1` 的话这条当场红，
   而只测起爆当帧的写法对它是瞎的。

### 11.4 不新增金向量场景

理由明说：金向量闸门抓的是**跨平台分歧**，而时停全是整数比较与分支，**没有引入任何新的平台
风险面**（无新浮点、无新表、无新数学核路径）。加一段只会让金向量更长而抓不到额外东西。

## 12. 版本与预算影响

- **`ENGINE_VER` 14 → 15**。四个理由任一即足：`World` 变宽（布局）、号表新增 513/560、
  输入词表新位、`WorldTables` 加 `BombCfg`（表 `content_hash` 变 ⇒ 身份三元组变）。
- **金向量必然改变**（新字段进哈希，同道具池刀的道理）。形态可解释，不是行为回归。
- **`World` 尺寸哨兵会红**：按它自己的四项清单（`copy_into` / checksum / D10 / SaveBytes）
  逐条判定后更新；`docs/pool-memory-layout.md` 与 `stg-world-design.md` D10 表同步。
- **容量约束（必须记进 D10 表旁）**：`TIMESTOP_FRAMES = 180` × 满火力约 1 发/帧 ≈ 180 发冻结
  自机弹，对 `ShotPool` 的 1024 是安全的。但 **`TIMESTOP_FRAMES` 一旦调到接近 1024，满火力下
  自机弹池会被打满、多出的弹静默不生成**（P4-a，同 F12 那一类）。这是**参数约束不是 bug**，
  但必须写下来——否则将来有人把时长调成 10 秒时会撞上一个查不出来的"弹变少了"。
- **道具池的第二个压力源**：bomb 的持续消弹 × 120 帧 ⇒ 星星按 1:1 生成，**再叠加全屏吸取**。
  这是 F12 那条路的第二个入口（第一个是收卡消弹）。实施时必须**实测一次满屏 bomb 的道具
  峰值**，与 `TIMESTOP_FRAMES` 的自机弹账写在同一处。上一刀刚把道具池抬到 1024，此处要验它
  还够。

## 13. 明确不做 / 已知边界

- ECL 侧**没有**"停敌人"的入口（那是玩家技能专属）。将来要，就是多一个 syscall 写
  `freeze_left[0]`，机制已经在。
- 时停**没有冷却、没有渐入渐出**（后者归表现层）。
- 不做实体级冻结（§7）。
- 不改 `World.frame` 的推进（§5）。
- **不给 `FieldPool` 加形状**。`FieldPool` 只有圆（`x`/`y`/`radius`）。"锁定敌人的 bomb"
  **不需要**引擎改动（圆心来源加一个 `BombOrigin` 变体 + 上层每帧重铺 `life = 1`，"跟随 =
  每帧重铺"是 `FieldPool` 设计时就写好的用法）；但**"激光形状的 bomb"必须动引擎**——要给
  field 加形状字段并在碰撞行 6/7 加第二种判定，那是**改碰撞矩阵**（`CLAUDE.md` 自检清单
  第 3 条：过评审）。**任何"通用口子"都变不出新形状来**，这条如实记下，免得后人以为留了
  描述层就万事大吉。将来真要做，另开一刀。

## 14. 未决 / 留给实施计划

1. **是否真的抽出共用的自机能力函数**（§8）——按实施时的代码形状定。过早抽象与写两遍同样
   是成本。本 spec 只承诺"两者的门禁与扣费顺序一致"，那是可测的性质。
2. **`TIMESTOP_FRAMES` 是否也该迁进 `CharacterCfg`**。bomb 的数字进了表，时停的没进（它不在
   任何表里，是引擎常量）。若将来"每个自机的时停时长/次数不同"成为内容需求，迁移路径与
   `BombCfg` 完全同构。本刀不做，记在这里免得将来当成疏漏。
3. **是否顺手实现 `checksum_report()`**（follow-ups **F13**）。§11.1 那条主测**不依赖它**，
   有它的话红了能直接指名字段、没有它只能说"有东西变了"。不是本刀前置。
4. **`BOMB_DMG_PER_FRAME = 4` 与 `BOMB_RADIUS = 120` 是内容期调参**，不是引擎裁定。首版按
   "120 帧 ≈ 480 伤害 ≈ 半管风铃卡血"取，内容线上再校。
