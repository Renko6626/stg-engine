## 结论（帧预算 16667 µs @60Hz）

1. **模拟本体极其便宜**：满池 8192 哑弹 ≈ 110µs = **0.7% 帧预算**；变换弹逐帧 sincos
   回填约为哑弹 4-5× 单价，段池满载 2048 发也只 ~300µs；真实游戏规模（~200 弹全机制
   混合）≈ 20µs。**ECL 指令预算可以定得很宽裕**——以 ~10ns/指令估算，每帧 1 万条指令
   ≈ 100µs 量级，完全可负担（M1 grill 时以此定防死循环上限）。
2. **校验和是最大单项成本**（1.3-2.1ms/帧，为 step 本体的 10-20×）：FNV-1a 逐字节扫
   0.92MB 所致。金向量/CI 逐帧算无碍（离线）；**联机随包 K=20 采样的既定设计被实测
   证实必要**（摊薄后 ~70µs/帧）；将来若在意可议分块/增量哈希，现无必要。
3. **rollback 完全可行**（M3 定心丸）：快照 memcpy 170-460µs、16 帧环 14.7MB；
   最坏 16 帧重演 ≈ 16×300µs ≈ 5ms，一帧预算内吃得下。
4. p99 尾部（数百 µs 级）主要是 Windows 调度噪声与批量补弹帧，非模拟本身的病态路径。

## syscall 号表百分区重排的派发代价（2026-07-31，A/B 实测）

spec `2026-07-31-syscall-renumber-design.md` §5 明文要求实测一件事：`ecl::syscall::dispatch`
的 `match` 从**稠密**（0–90）变**稀疏**（0–741），rustc 可能从跳转表退化成二分查找，而
syscall 派发在热路径上（每次 `OP_SYS` 都走）。**结论：没有退化，无可测回归，派发实现不动。**

### ⚠️ 先记一条坑：本仓的 `bench` 对这件事**结构性失明**

`bench` 的四类场景（哑弹 / xform / 全混合）**全部**传 `EclImage::empty()`——零任务、零
`OP_SYS`。**它一条 syscall 都不执行**，所以拿它的前后对比来回答 §5 是无效的。前后各跑一轮，
差异全在热漂移噪声里（首行 1647.7 → 1959.7 µs 的校验和是预热假象，其余各档 ±1%）：

| 场景 | step 均 µs（重排前） | step 均 µs（重排后） |
|---|---|---|
| 哑弹 1024 | 11.7 | 12.4 |
| 哑弹 2048 | 18.9 | 18.8 |
| 哑弹 4096 | 35.8 | 35.7 |
| 哑弹 8192 | 68.9 | 69.5 |
| xform 512 | 31.5 | 31.3 |
| xform 1024 | 60.7 | 60.6 |
| xform 2048 | 118.8 | 118.6 |
| 全混合 | 6.1 | 6.1 |

> 下次有人要量"VM/syscall 改动"的代价，别只跑 `bench`——**先确认场景里有没有脚本在跑**。
> 要给 `bench` 补一档 ECL 场景是独立一刀（记在 `follow-ups.md`）。
>
> **（2026-08-01 追记，只加指路不改上面任何数字）** 那一刀已经落地：`bench` 尾部现有
> 三个跑真脚本的饱和档（`ecl 任务 256` / `syscall 密` / `shooter 大环`）。本节这句
> "结构性失明"从此**只对 2026-07-31 及之前的 `bench` 成立**——现在量 VM 改动直接跑
> `bench` 看 `syscall 密` 那行即可，见本文件末节。

### 真正的判据一：反汇编（结构，比时间硬）

`objdump -d target/release/stg-harness`，取 `ecl::syscall::dispatch` 函数体：

| | 重排前（0–90 稠密） | 重排后（0–741 稀疏） |
|---|---|---|
| 派发形态 | `cmp $0x5a` + **1 张**跳转表 | `cmp $0x294` + **2 张**跳转表（0..=660 / 661..=741） |
| 间接跳转 `jmp *` | 1 | 2 |
| 函数指令数 | 1217 | 1230（**+13**） |
| 条件分支 | 145 | 146（**+1**） |
| 跳转表 rodata | 91 项 = 364 B | 742 项 = 2968 B（**+2.6 KB**） |

**仍是 O(1) 间接跳转，没有退化成二分。** 代价是多一次范围比较（只落在 `7xx` 族那 7 条的
路径上）+ 2.6 KB 只读表（`.rodata`，按 cache line 取用，实际驻留的只有被走到的那些项）。

### 真正的判据二：一个 ~100% 打在派发上的合成负载

外挂一个临时 crate（不进仓库）：60 个任务 × 220 条 syscall/帧，号覆盖 `0xx`（12 条引擎变量）
/ `1xx`（8 条查询）/ `7xx`（`global`）三段号域——即前后两版分别踩到"跳转表内 / 跨两张表"两种
路径。同一台机、交替跑、各取 5 轮最小值：

| | 重排前 | 重排后 |
|---|---|---|
| 三轮最好值（µs/帧，13 200 syscall/帧） | 133.24 / 133.33 / 133.41 | 133.58 / 133.96 / 134.26 |

**+0.3~0.6%**，换算 **≈ 0.04 ns/syscall**（亚周期）。这个负载里 step 本体几乎无事可做，
133 µs 基本全是 syscall 执行本身——也就是说，在**最坏可能的放大倍数**下差异也只有半个百分点；
真实场景（`golden` 的风铃卡、demo 局）里量不出来。

**处置：不启用 spec §5 的备选方案**（按族 `n / 100` 先分派、族内偏移查表）。rustc 自己给出的
两表方案已经是 O(1)，手写分派换不来什么，只会多一处要维护的号表镜像。

### 逐档读法

**① `ecl 任务 256` ≈ 29 µs = 0.18% 帧预算。** 这是**纯调度价**：256 个任务每帧各跑
`WAIT`+`JMP` 两条指令，世界本体零弹零敌。摊到每任务 **≈ 114 ns/帧**，其中真正的指令执行
只有两条——绝大部分是 `run_tasks` 的存活位扫描 + `Task` 的 copy-out/copy-back +
owner 门禁/预算分账。**推论：把任务池填满不是性能问题**，256 只敌各挂一个主任务的关卡
可以放心写。

**② `syscall 密` ≈ 408 µs = 2.4% 帧预算，是四档里最贵的一档。**

先说这一档的两个数是**怎么算出来的**（不是拍的）：

- **syscall 条数 = 15 240 条/帧**，纯构造式计数：`bench_sys_burn` 的内层每轮固定 9 条
  （`$frame`/`$self_age`/`$self_hp`/`rand`/`global` 五条 + `$self_x`/`$self_y`/
  `$player_x`/`$player_y` 四条），循环体**无分支**故动态数 = 静态数 × 迭代数；单任务
  = 9 × 28 + 2（每帧两条 `set_global`）= **254 条**，× 60 个任务 = 15 240。
  （`sin`/`cos` 是 VM op 不是 syscall，故刻意没用；`$` 引擎变量读取**每次都是**一条
  `OP_SYS`，见 ecl-lang.md。）
- **总指令数 ≈ 56 520 条/帧**，靠**撞两条预算的边界**反解出来：单任务预算 1024 条在
  `BURN_ITERS` = 30→31 之间翻车，全局预算 65536 条在 `BURN_TASKS` = 69→70 之间翻车
  （70 时恰好 1 个任务饿死，71 时 2 个——共享余额按池索引升序消耗，从尾巴开始死，I4）。
  两条边界联立 ⇒ **单任务 ≈ 942 条/帧**（每轮 ≈ 33 条 + 每帧固定 ≈ 18 条），× 60 = 56 520。

于是：**≈ 26.8 ns/syscall**（408.0 µs ÷ 15 240，含它周围那两三条压栈/算术指令）、
**≈ 7.2 ns/指令**（408.0 µs ÷ 56 520），派发密度 254/942 ≈ **27%**。
这条数与 M0-18 结论 1 当年"以 ~10 ns/指令估"的估算**对上了**，那条估算就此从估算变成实测。
> 号表重排刀记的 "+0.04 ns/syscall" 是在这个量级上谈的——26.8 ns 的 0.15%，确实量不出来。
> **下次再动 `ecl::vm`/`ecl::syscall`，跑 `bench` 看这一行就够了，不必再外挂临时 crate。**
> 注意这一档是**病态密度**：真实脚本一帧几百条 syscall 是常态，此处是它的几十倍。

**③ `shooter 大环` ≈ 50 µs，其中开火本身只占一小半。** 稳态 5982 颗弹已经贵过
「哑弹 4096」（35.6 µs）而便宜过「哑弹 8192」（69.1 µs），落在那条曲线上——也就是说
**204 颗/帧的 `sh_fire` 摊下来只有十几 µs，网格循环 + 逐颗 `create_bullet` 不是瓶颈**，
瓶颈仍是那 6000 颗弹的逐帧积分与碰撞。p99（68）比 p50（51）高出的那一截是开火那一帧的
255 颗批量分配。

**④⑤ 笛卡尔回填的价钱 = 两行之差 ≈ 8.5~11.4 µs/帧**（三轮：11.4 / 8.7 / 8.5；第一轮
偏热，后两轮一致）。除以 256 只敌 ⇒ **每次 `backfill_enemy_polar` ≈ 33~45 ns**，即
一次 `isqrt` + 一次**钉死 16 轮**的 CORDIC `atan2`。这是敌人运动动词族刀（2026-07-31）
把 `move_vel_xy` 加进热路径时引入的、此前从没量过的开销。
> **处置：不优化。** 满编 256 只敌全程笛卡尔插值（现实里根本不会发生——敌人多半在走
> `move_to` 或匀速直线）也只有 0.09% 帧预算；而回填是**语义必需**的：不回填
> `$self_speed`/`$self_angle` 就会读到陈值，那是双表示的火药桶。
> 极坐标那行（5.9 µs）几乎全是 256 只敌的积分与碰撞本体，插值本身（两次查表）近乎免费。

### 结论增补（帧预算 16667 µs @60Hz）

1. **四根轴各自打满，加起来也不到 3.1% 帧预算**（29 + 408 + 50 + 19）。M0-18 那条
   "模拟本体极其便宜"的结论在接上 ECL/发射器/敌人运动之后**依然成立**。
2. **校验和仍是最大单项**（~1646 µs，为四档 step 之和的 3 倍）——与第二/三轮同一结论，
   联机 K=20 采样的既定设计继续被坐实。
3. 唯一值得盯的是 **`syscall 密`**：它是四档里唯一一个能在真实脚本里被"作者写法"推上去的
   轴（弹和敌有池上限兜底，指令数没有——只有 `TASK_BUDGET`/`GLOBAL_BUDGET` 兜底）。
   全局 65536 条/帧的上限按 7.2 ns/指令折算 ≈ **473 µs/帧 = 2.8% 帧预算**，也就是说
   **VM 预算上限本身就是一道够用的性能护栏**，不需要另设。
