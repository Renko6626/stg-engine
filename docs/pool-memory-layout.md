# 池内存布局：SoA 与缓存精算

面向：池框架 / 相位循环 / 性能调优。相关：`define_pool!`（stg-derive）、D2 / §3.1 / I7、§9 基准。

---

## 0. 我们用 SoA（Structure of Arrays），不是 AoS

`define_pool!` 展开出**每个字段一条数组**，装所有实体的同一字段：

```rust
struct BulletPool {
    x:  [Fx; 8192],   // 所有弹的 x，连续
    y:  [Fx; 8192],   // 所有弹的 y
    vx: [Fx; 8192], vy: [Fx; 8192],
    // ... 其余 15 字段各一条
    generation: [u16; 8192], alive: [u64; 128],
}
```

一颗弹的数据**分散**在各字段数组的同一下标 `i`（`x[i]`, `y[i]`…）。对立面 **AoS**（`[Bullet; 8192]`、每弹字段挨一起）**不用**。

**为何 SoA**：热循环只碰用到的字段（缓存线满载）、SIMD 向量化、字段级 Checksum 整条哈希天然跳 padding（D11 前提）、numpy/MultiMesh 零拷贝视图（A9）。SoA 短板是"随机取单实体全字段要跳 N 条线"——但 danmaku 相位全是**批量按字段扫**，正好避开。

## 1. 数据尺寸

> ⚠️ **字段不是一律 4B**——弹池 20 个字段里近半是 `u8`/`u16`（`sprite`/`life`/`xform_wait` 是
> u16，`delay`/`flags`/`grazed_by`/`xform_next` 是 u8，`ang_vel` 是 i16）。按“全 4B”估会把
> 弹池算成 625 KB，虚高 30%。下表是**实测**（`size_of`），不是估值。

| 集合 | 大小 |
|---|---|
| 单个 4B 字段数组（如 `x`） | 8192 × 4B = **32 KB** |
| **积分热集** `x,y,vx,vy`（全 4B） | 4 × 32KB = **128 KB** |
| 弹池全 20 字段 + gen/alive | 56 B/弹 × 8192 + 17 KB = **476 160 B ≈ 465 KiB**（表现契约 v2 起含 `born_frame: u32`，模拟相位不读，只有编码器读） |

六个池的实测总账（`gen: u16×cap` 与 `alive: u64×⌈cap/64⌉` 已计入）：

| 池 | cap | 每槽字节 | 池总量 |
|---|---|---|---|
| `BulletPool` | 8192 | 56 | 476 160 B ≈ 465 KiB |
| `XformSegPool` | 4096 | — | 393 472 B ≈ 384 KiB |
| `ShotPool` | 1024 | — | 28 800 B ≈ 28 KiB |
| `EnemyPool` | 256 | 109 | 28 448 B ≈ 27.8 KiB |
| `ItemPool` | 1024 | 22 | 22 656 B ≈ 22.1 KiB |
| `FieldPool` | 16 | — | 328 B |

**这张表由 `step.rs` 的 `pool_size_sentinel_guards_the_layout_doc_account` 押运**：池宽了而
账没跟，测试就红——这份文档做的是缓存精算，账过期等于第 2 节整篇推论悄悄失效
（此前正是这么过期的，见 follow-ups C21）。

## 2. 缓存精算（开发机 i7-8750H 为例；原理通用于任何现代 CPU）

每核私有：**L1D 32 KB（8-way）· L2 256 KB · L3 9 MB 共享**。

- **积分热集 128KB → L2 驻留**（占半个 L2）。不驻 L1D（32KB 装不下 4 条），但不需要——积分是**顺序流式**扫描，L1D 只需装"移动窗口"，硬件预取器（next-line/stride）把 L2→L1 延迟藏掉。
- **cache line 64B = 16 个 Fx**，SoA 顺序访问 → 每条线满载 16 个有用值，零浪费。
- **每相位只碰字段子集**（积分 x/y/vx/vy=128KB；碰撞 x/y/radius 三条 4B + flags 一条 u8 = 3×32KB+8KB≈104KB——窄字段让它比按 4B 估的 160KB 更小），都塞得进 256KB L2。**永远不需要 20 字段同时热**——SoA 红利。
- **最低空位分配的附赠**：活跃弹聚低索引 → 稀疏时每条数组"被碰前缀"小（2000 弹 → 4×8KB=32KB ≈ 整个塞进 L1D）。

## 3. 成本精算（4000 弹积分，设计目标）

- 搬运 ≈ 4000×4B×4 = **64 KB**，从 L2 拉 ≈ **~0.4 µs**。
- 计算 ≈ 8000 次 i32 加（`pos+=vel`），AVX2 一次 8 个 → ~1000 指令 ≈ **亚 µs**（x、vx 各自连续，向量化完美）。
- 合计 **~1 µs ≈ 0.5ms 单步预算的 0.2%**。**积分不是瓶颈**——吃预算的是碰撞（O(N×M)）与 ECL VM。

## 4. 暗礁：数组大小 = L1D 大小 → 同组映射

弹池单数组 **32KB 正好 = L1D 大小** → `x[i]`、`y[i]`、`vx[i]`、`vy[i]`（相隔整数倍 32KB）**映射到同一个 L1 组**。好在 **L1D 8-way**：积分同时碰 4 条 ≤ 8 路、碰撞碰 ~5 条 ≤ 8 路，**8 路刚好吸收**，不抖动。

⚠️ **若将来某相位同时热访问 > 8 个字段** → L1 冲突失效抖动 → 解：给数组容量**加几个哨兵元素**（`[Fx; cap + 8]`）打破 2 的幂对齐。现在 ≤5 路/相位，安全。

## 5. 结论与纪律

- **当前 SoA 布局对目标负载是缓存最优的，不改。**
- **不做投机的 AoSoA / hot-cold 字段拆分**（会伤 SIMD + 打乱 Checksum 整条哈希 / zero-copy 视图的整洁）——仅当 §9 基准**实测**积分成 stream/conflict 瓶颈才重新考虑。
- **M0-4/M0-5 把"8192 满池单步时延"纳入 §9 CI 基准**（三平台各测），用实测钉死数字。按上面精算，积分会稳在个位数 µs。
